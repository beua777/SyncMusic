# SyncMusic 개발 계획서

> 삼성 뮤직처럼 생긴 **나만의 Windows 음악 플레이어** + 같은 Wi-Fi에서 **갤럭시 폰과 자동 동기화**
> 작성일: 2026-10-23 · 버전 0.1 (MVP)

---

## 1. 목표

| # | 목표 | 완료 기준 |
|---|------|-----------|
| G1 | 디자인을 삼성 뮤직(One UI)과 최대한 비슷하게 | 탭(트랙·재생목록·앨범·아티스트·폴더), 큰 제목 헤더, 둥근 카드, 하단 미니 플레이어, 앨범 색이 배어나는 전체 재생 화면 |
| G2 | 같은 Wi-Fi면 자동 동기화 | 폰 앱이 15분마다(+앱을 열 때) PC를 찾아서 음악 파일과 재생목록을 주고받음 |
| G3 | 재생목록 곡 순서 유지 | 폰↔PC를 몇 번 오가도 순서가 그대로이고, 양쪽에서 동시에 고쳐도 3-way 병합으로 순서 보존 |
| G4 | 삼성 뮤직과 같은 셔플·반복 규칙 | 아래 5장의 규칙을 자동 테스트로 고정 |

## 2. 조사 결과: 먼저 알아야 할 제약

| 사실 | 영향 | 대응 |
|------|------|------|
| 삼성 뮤직은 다른 앱이 재생목록을 읽고 쓰는 API를 주지 않음 (내부 DB) | 폰 앱이 삼성 뮤직 재생목록을 직접 읽을 수 없음 | 삼성 뮤직 **설정 → 플레이리스트 관리**의 기능을 이용 (아래) |
| 플레이리스트 관리에 **폴더 선택**, **모든 플레이리스트 내보내기**, **플레이리스트 가져오기**, **모든 플레이리스트 자동 백업**(바뀔 때마다 폴더에 저장)이 있음 | 자동 백업을 켜면 재생목록이 바뀔 때마다 순서가 담긴 파일이 생김 | 동반 앱이 그 폴더를 읽어서 순서 그대로 PC로 보냄 → **폰→PC는 완전 자동** |
| 가져오기는 내장 메모리의 `.m3u`가 잘 되고 `.m3u8`은 안 된다는 사용자 보고가 있음. 구형 기기는 `.smpl` 형식으로 내보냄 | 형식이 기기마다 다름 | 읽을 때는 `.m3u` `.m3u8` `.smpl` 모두 지원, 쓸 때는 `.m3u`(UTF-8) |
| 내보낸 파일은 절대 경로(`/storage/emulated/0/...`)라서 기기가 바뀌면 경로가 깨진다는 보고가 있음 | 경로로 곡을 맞추면 깨지기 쉬움 | 곡을 **파일 내용 해시(quick hash)** 로 식별하고, 안 맞으면 제목·가수·길이로 맞춤 |
| 외부 앱은 삼성 뮤직 DB에 재생목록을 쓸 수 없음 | PC에서 바꾼 재생목록을 삼성 뮤직에 바로 넣을 수 없음 | 동반 앱이 `.m3u`를 그 폴더에 써 두고 알림 → 삼성 뮤직에서 **가져오기를 한 번 누르면 반영** |
| 음악 파일은 MediaStore에 넣으면 삼성 뮤직이 자동으로 인식 | 파일 동기화는 양방향 자동 가능 | 동반 앱이 `Music/SyncMusic/`에 저장 |
| 삼성 뮤직의 셔플 알고리즘은 비공개 | 똑같은 난수열을 낼 수는 없음 | 공식 도움말에 나온 **겉으로 드러나는 규칙**을 재현 (5장) |
| 이 PC는 Smart App Control이 새로 빌드한 DLL을 막는 일이 있음 | .NET/Electron 직접 빌드 앱은 실행이 막힐 위험 | 서명된 `node.exe` + Edge 앱 창(`msedge --app`)으로 실행 → 막힐 바이너리가 없음 |

출처: 삼성전자서비스 "삼성 뮤직 플레이리스트 내보내기/가져오기", Samsung UK "How to use Samsung Music", Samsung AU "Importing and Exporting Samsung Music Playlists", Samsung Community 게시글 (README의 링크 참고).

## 3. 전체 구조

```
┌──────────────── Windows PC ────────────────┐                ┌──────────────── 갤럭시 폰 ────────────────┐
│  Edge 앱 창 (UI: HTML/CSS/JS, PWA 설치 가능)│                │  삼성 뮤직 (평소처럼 사용)                 │
│        │ 127.0.0.1:47810 (이 PC에서만 접속) │                │     │ 자동 백업 폴더(.m3u)   │ MediaStore │
│  SyncMusic 서버 (Node.js 24)                │                │  SyncMusic 동반 앱 (Kotlin)                │
│   ├ 라이브러리: 폴더 감시, 태그·커버·가사   │  UDP 47812     │   ├ PC 찾기 (브로드캐스트)                 │
│   ├ 재생목록·재생 상태 저장 (JSON)          │ ◀──── 찾기 ─── │   ├ 6자리 코드 페어링 (ECDH)               │
│   └ 동기화 서버 0.0.0.0:47811               │ ◀── 서명 요청 ─▶│   ├ 15분마다 Wi-Fi일 때 동기화 (WorkManager)│
│      (HMAC 서명 없는 요청은 거부)           │   HTTP 47811   │   └ 이어듣기: 삼성 뮤직 재생 정보 → PC      │
└─────────────────────────────────────────────┘                └────────────────────────────────────────────┘
```

- UI 서버(47810)는 `127.0.0.1`에만 열려서 같은 Wi-Fi의 다른 기기가 접근할 수 없음. Host·Origin 헤더도 검사(DNS 리바인딩·CSRF 방지).
- 동기화 서버(47811)만 Wi-Fi에 열리고, `hello`/`pair`를 뺀 모든 요청은 페어링 때 만든 비밀키로 서명해야 함. PC 응답도 서명되어 폰이 가짜 PC를 거부함.

|------|------|------|

## 5. 셔플·반복 사양 (삼성 뮤직 규칙 재현)

`pc/public/js/queue.js`의 `PlayQueue`가 구현하고 `pc/test/queue.test.js`가 검증합니다.

| # | 삼성 뮤직 동작 | SyncMusic 구현 |
|---|----------------|----------------|
| S1 | 셔플은 선택한 곡들을 무작위로 재생 | Fisher–Yates로 **한 바퀴 동안 중복 없이** 섞은 순서를 만듦 |
| S2 | 재생 중 셔플을 켜면 듣던 곡은 계속 나옴 | 현재 곡을 맨 앞에 두고 나머지를 섞음 |
| S3 | 셔플을 끄면 원래 목록 순서로 이어짐 | 현재 곡의 원래 위치부터 목록 순서대로 |
| S4 | 반복 버튼: 반복 안 함 → 전체 반복 → 한 곡 반복 | 같은 순서로 순환 (아이콘도 A→ / 반복 / 1) |
| S5 | 이전 버튼: 한 번 누르면 곡 처음으로, 두 번 누르면 이전 곡 | 3초가 지났으면 처음으로, 3초 안이면 이전 곡 |
| S6 | 한 곡 반복 중 다음 버튼은 다음 곡으로 | 곡이 **끝나서** 넘어갈 때만 같은 곡 반복 |
| S7 | 재생 순서(Order) 화면에서 다음에 나올 곡을 보고 끌어서 바꿈 | 셔플 중이면 섞인 순서 그대로 보여주고, 끌어서 바꾸면 그 순서로 재생 |
| S8 | 반복 안 함이면 목록을 한 번 재생하고 멈춤 | 마지막 곡이 끝나면 첫 곡에서 일시정지 상태 |
| S9 | (관찰) 전체 반복 + 셔플 | 한 바퀴가 끝나면 다시 섞되 방금 들은 곡이 첫 곡이 되지 않게 |
| S10 | 앱을 다시 열면 듣던 곳부터 | 섞인 순서·위치·재생 시간까지 저장 → 재시작해도 셔플 순서 유지 |
| S11 | 목록에서 곡을 누르면 그 곡부터 | 기본은 셔플 상태 유지. 설정의 "곡을 누르면 목록 순서대로"로 삼성 도움말에 적힌 '셔플 무시' 동작도 선택 가능 |
| S12 | 대기열 추가 위치: 현재 곡 다음 / 맨 끝 | `다음에 재생`, `재생 대기열에 추가` 둘 다 제공 (셔플 중에도 섞인 순서에 반영) |
| S13 | 폰에서 듣던 대기열 이어받기 | 받은 순서를 섞지 않고 그대로 이어서 재생 (셔플 표시는 폰 상태 따름). 폰이 재생 중이었으면 지난 시간만큼 앞으로 당기되 곡 끝을 넘지 않게 |

난수는 시드가 있는 PRNG(mulberry32)를 써서 테스트에서 재현할 수 있게 했습니다.

## 6. 동기화 설계

### 6.1 PC 찾기
폰이 `255.255.255.255:47812`와 Wi-Fi 브로드캐스트 주소로 `{"t":"discover","app":"SyncMusic","v":1}`를 보내면, PC가 `{"t":"here","pcId","pcName","port":47811}`로 응답. 공유기가 기기 간 통신을 막는 경우(AP 격리)를 위해 IP 직접 입력도 지원.

### 6.2 페어링 (6자리 코드 + ECDH)
1. PC 설정 화면에서 **새 휴대폰 연결** → 6자리 코드 3분간 표시
2. 폰: P-256 키쌍 생성, `proof = HMAC(code, "pair1|deviceId|phonePub")`와 함께 전송
3. PC: proof 확인(5번 틀리면 코드 폐기) → PC 키쌍 생성 → 서로의 공개키로 ECDH → `secret = HKDF-SHA256(ecdh, salt=code, info="SyncMusic pair v1|deviceId|pcId")`
4. PC도 `HMAC(code, "pair1-ok|pcId|pcPub|phonePub")`로 증명 → 폰이 확인
→ Wi-Fi를 엿보는 사람은 코드를 알아도 비밀키를 계산할 수 없음 (ECDH). 실시간 중간자 공격까지 막으려면 다음 단계에서 PAKE/TLS 고려.

### 6.3 요청 서명
```
X-SM-Device: <deviceId>
X-SM-Time:   <unix ms>          (±5분 넘으면 거부)
X-SM-Body:   <sha256(body) hex>  (업로드는 받으면서 검증)
X-SM-Sig:    base64(HMAC-SHA256(secret, METHOD \n PATH?QUERY \n TIME \n BODYHASH))
응답의 X-SM-Sig: base64(HMAC-SHA256(secret, "resp" \n 요청서명 \n sha256(응답본문)))
```
파일 다운로드 응답은 본문 대신 받은 파일의 quick hash가 요청한 ID와 같은지로 검증.

### 6.4 곡 식별: quick hash
```
qh = hex( SHA-256( size(8바이트 빅엔디언) ‖ 앞 64KiB ‖ 뒤 min(64KiB, size−64KiB) ) )[0:32]
```
- 같은 파일이면 폰과 PC에서 같은 값 → 경로가 달라도 같은 곡
- PC는 이 값을 곡 ID로 씀. 태그를 고쳐서 값이 바뀌면 같은 경로의 옛 ID를 새 ID로 바꿔서 재생목록이 깨지지 않음
- 내용이 다른 같은 곡(다른 인코딩 등)은 `제목+가수` 정규화 + 길이 ±2초로 맞춤 (중복 업로드 방지)

### 6.5 동기화 한 번의 흐름
```
폰                                              PC
 │ UDP discover ───────────────────────────────▶ │
 │ ◀─────────────────────────────── here (port) │
 │ POST /sync/manifest {곡 목록, 재생목록}  ───▶ │ 곡 매칭, 재생목록 3-way 병합
 │ ◀──── {upload:[...], download:[...], playlists:[...], syncId} │
 │ PUT /sync/file/<qh> (폰에만 있는 곡) ───────▶ │ 해시 검증 → "From Phone" 폴더 → 라이브러리
 │ GET /sync/file/<id> (PC에만 있는 곡) ◀───── │
 │   → MediaStore Music/SyncMusic/ 저장 → 삼성 뮤직이 자동 인식
 │   → 재생목록 .m3u 쓰기 → "삼성 뮤직에서 가져오기" 알림
 │ POST /sync/commit {결과} ──────────────────▶ │ 기준점 갱신, 로그
```
- 한 번에 다 못 옮겨도(WorkManager 10분 제한) 다음 실행 때 이어서 함 (파일 단위로 멱등)
- PC→폰 범위는 PC 설정에서 기기별로: **재생목록에 있는 곡만**(기본) / 전체 / 안 함

### 6.6 재생목록 3-way 병합 (순서 유지)
기준점 B(양쪽이 마지막으로 같았던 내용), PC 현재 C, 폰 현재 P:
1. `C == B` → P 채택 / `P == B` → C 채택 / `C == P` → 그대로
2. 둘 다 바뀌었으면 최근에 바뀐 쪽을 **주(primary)** 로 삼아 그 순서를 그대로 쓰고
3. 반대쪽에서 지운 곡은 빼고
4. 반대쪽에서 새로 넣은 곡은 반대쪽 목록에서 **바로 뒤에 있던 곡 앞**에 끼움 (뒤에 아무것도 없으면 맨 끝)
5. 같은 곡이 여러 번 들어간 경우는 `id#몇번째`로 구분

예) B=`[a,b,c]`, PC가 `x`를 a 뒤에 추가 → C=`[a,x,b,c]`, 폰이 역순으로 바꿈 → P=`[c,b,a]` (폰이 최근)
→ 결과 `[c,x,b,a]`

기준점은 **양쪽에서 같은 내용이 확인됐을 때만** 앞으로 옮깁니다. PC가 써 둔 `.m3u`를 사용자가 아직 가져오지 않았는데 삼성 뮤직 자동 백업이 옛 내용으로 덮어써도, PC 변경이 사라지지 않고 다시 보내집니다.

### 6.7 삭제 정책 (안전 우선)
- 음악 **파일 삭제는 동기화하지 않음** (실수로 지워도 반대쪽엔 남음)
- 폰에서 재생목록 파일이 사라지면 PC 재생목록은 남겨 두고 연결만 끊음 (로그 표시)
- PC에서 재생목록을 지우면 폰에 써 둔 `.m3u`만 지우고, 삼성 뮤직 안의 재생목록은 직접 지우라고 안내 (외부 앱이 지울 수 없음)

## 7. 데이터 저장

PC: `%LOCALAPPDATA%\SyncMusic\` (테스트할 땐 `SYNCMUSIC_DATA`로 바꿈)

| 파일 | 내용 |
|------|------|
| `settings.json` | 음악 폴더, 테마, 재생 옵션, 기기별 동기화 옵션 |
| `library.json` | 곡 목록 (ID=quick hash, 경로, 태그, 재생 횟수) |
| `playlists.json` | 재생목록 (곡 ID 배열 = 순서), 삭제 기록 |
